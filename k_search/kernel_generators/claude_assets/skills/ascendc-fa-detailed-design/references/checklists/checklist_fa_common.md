# FA 通用检查模块（F1-F8）

适用于所有 FA 类算子，所有开发场景（S1-S4）。

---

## 【F1】流水阶段划分（必填，不可跳过）

### S4（全新 FA）

```
问题：请设计 Cube+Vector 流水阶段划分。

对每个流水阶段，需明确：
  (1) 阶段编号和名称（如 C1-BMM1, V1-Softmax, C2-BMM2, V2-Update）
  (2) 执行核类型：AIC（Cube）或 AIV（Vector）
  (3) 计算内容描述
  (4) 输入数据来源（从哪个 buffer/哪个阶段的输出）
  (5) 输出数据去向（写到哪个 buffer/传给哪个阶段）
  (6) CV 比例：AIC:AIV = 1:N（如 1:2 表示 1 个 Cube 核配 2 个 Vector 核）

典型 FA 前向流水示例（FAS 基座）：
  C1(BMM1: Q×K^T) → V1(Softmax: scale+mask+exp+sum) → C2(BMM2: P×V) → V2(Update: Online rescale)

典型 FA 反向流水示例（FASG 基座）：
  C1(dO×V^T) → V1(dS处理) → C2(dS×K) → V2(dQ累加) → C3(dS^T×Q) → V3(dK累加) + V4(dV)
```

### S1/S2/S3（增量）

```
问题：基于基座算子的流水设计，确认：
  1. 基座流水阶段是否完全继承？
  2. 若有修改：
     - 新增了哪些流水阶段？
     - 删除了哪些流水阶段？
     - 修改了哪些阶段的计算内容？
  3. CV 比例是否变化？
  4. 修改后的完整流水阶段列表

⚠️ 注意：修改流水阶段会连锁影响同步事件（F2）和 Buffer 设计（F4），
        必须三者联动更新。
```

## 【F2】核间同步设计（必填，不可跳过）

### S4（全新 FA）

```
问题：请设计 AIC/AIV 核间同步事件。

对每个同步点，需明确：
  (1) 事件 ID（数值）
  (2) 发送方（AIC / AIV0 / AIV1）
  (3) 接收方（AIC / AIV0 / AIV1）
  (4) 同步语义（如"C1 完成 BMM1，通知 V1 可以开始 Softmax"）
  (5) 对应的 SetFlag/WaitFlag 调用

关键约束：
  - AIC→AIV 和 AIV→AIC 使用 CrossCoreSetFlag/CrossCoreWaitFlag
  - AIV1 的事件 ID = AIV0 的事件 ID + 16（910B 的偏移规则）
  - 同一事件不能同时被两个消费者 Wait（需拆分为多个事件）
  - Ping-Pong 模式下，奇偶迭代使用不同事件 ID 集合

典型同步矩阵（FAS 基座）：
  SYNC_C1_V1[0,1] : AIC→AIV, C1完成BMM1→V1开始Softmax
  SYNC_V1_C2[2,3,4]: AIV→AIC, V1完成Softmax→C2开始BMM2
  SYNC_C2_V2[5,6]  : AIC→AIV, C2完成BMM2→V2开始Update
```

### S1/S2/S3（增量）

```
问题：基于基座同步设计，确认：
  1. 基座同步事件是否完全继承？
  2. 若流水阶段有修改：
     - 需新增哪些同步事件？
     - 需删除哪些同步事件？
     - 事件 ID 是否有冲突？
  3. 列出完整的同步事件表
```

## 【F3】分核策略

### S4（全新 FA）

```
问题：数据按哪个轴分配到多个 AIV core？

关键决策点：
  - 切分轴（S 轴 / B×N 轴 / 其他）
  - 对称切分 vs 交错切分（多 AIV 核时）
  - 每核处理量计算公式
  - 负载均衡策略（余量分配）
  - 小张量保护（totalItems < usedCores 时的处理）

FA 典型模式：
  - 训练前向（FAS）：S1 轴切分，对称模式 or 交错模式
  - 训练反向（FASG）：S1 轴切分
  - 推理（FIAS/IFA）：B×N 轴切分
  - Prefill（PFA）：S 轴切分，支持 Padding 去除
```

### S1/S2/S3（增量）

```
问题：基座分核策略是否适用于新场景？
  - 若新增特性不影响数据切分：标注"继承"
  - 若新增维度/新增稀疏模式影响切分：设计新策略
```

## 【F4】Buffer 4 层设计（必填，不可跳过）

```
问题：请设计 4 层 Buffer 分配方案。

⚠️ 关键要求：每个 buffer 必须给出【实际字节数计算公式和结果】，
   最终必须进行【硬件容量约束校验】（使用率 + 通过/不通过判定）。
   不允许使用"—"或"与基座一致"代替具体数值。

### 步骤 0：确定关键维度参数

先从 Tiling 代码/概设/源码中提取以下参数的实际值（示例）：

  | 参数 | 值 | 来源 | 说明 |
  |------|---|------|------|
  | s1BaseSize | 64 | tiling.cpp | Query tile 行数 |
  | s2BaseSize | 128 | tiling.cpp | KV tile 列数 |
  | dSize / dBaseSize | 576 | tiling.cpp | head dim |
  | CV_RATIO | 2 | common.h | Cube:Vector 比 |
  | Q_T / sizeof | FP16 / 2B | OpDef | Query 数据类型 |
  | KV_T / sizeof | INT8 / 1B | OpDef | KV 数据类型 |

  这些参数是后续所有 buffer 大小计算的基础。

### L1（数据预加载层）
  - 存储内容：[Q/K/V 的哪些 tile]
  - Buffer 数量：[N-buffer 策略，如 3-buffer for l1KBuffers]
  - 【必填】大小公式：每个 buffer 的字节数计算
    格式：bufName = dim1 × dim2 × sizeof(dtype) × bufNum = xxx B = xxx KB
    示例：l1KBuffers = 576 × 128 × 2(fp16) × 3(triple) = 442,368 B = 432 KB
  - 预加载策略：[何时触发预加载、与 Cube 计算的重叠方式]
  - 【必填】L1 总使用量 = Σ 各 buffer 大小

### L0A / L0B / L0C（Cube 操作数层）
  - L0A 存储内容：[BMM 的左操作数，如 Q tile]
  - L0B 存储内容：[BMM 的右操作数，如 K^T tile]
  - L0C 存储内容：[BMM 输出，如 S tile]
  - Buffer 数量：[Double Buffer / 4-buffer 等]
  - 【必填】大小公式（同 L1 格式）
  - 大小约束：[L0A=64KB, L0B=64KB, L0C=256KB(A5)/128KB(A3)]

### UB（Vector 计算层）
  - 各 Buffer 列表：[名称、大小公式、大小结果、用途]
  - CrossCore 共享 Buffer：[哪些 buffer 被 AIC 和 AIV 共享访问]
  - 地址分配策略：[静态偏移 / 动态 AllocTensor]
  - 【必填】UB 总使用量 = Σ 各 buffer 大小

### Workspace（跨核通信层）
  - 使用场景：[确定性写回 / 跨核归约 / 中间结果暂存]
  - 【必填】大小计算：[workspace 总大小公式，含每项组成]
  - 写入/读取时序：[哪个阶段写、哪个阶段读]

### 【必填】硬件容量约束校验

必须输出以下汇总表，逐项校验：

  | 存储层级 | 硬件容量 | 代码初始化 | 实际使用 | 使用率 | 校验结果 |
  |---------|---------|-----------|---------|-------|---------|
  | UB | 248KB(A5)/192KB(A3) | xxx KB | xxx KB | xx% | ✅通过/❌超限 |
  | L1 | 1MB(A5)/512KB(A3) | xxx KB | xxx KB | xx% | ✅通过/❌超限 |
  | L0A | 64KB | 64KB | xxx KB | xx% | ✅通过/❌超限 |
  | L0B | 64KB | 64KB | xxx KB | xx% | ✅通过/❌超限 |
  | L0C | 256KB(A5)/128KB(A3) | xxx KB | xxx KB | xx% | ✅通过/❌超限 |
  | Workspace | GM | 动态 | xxx MB | — | ✅通过/❌超限 |

  使用率 > 90% 时需添加风险提示。
  校验不通过时必须提出解决方案（减少 bufNum / 缩小 tile / 分时复用等）。

硬件容量参考（A5/951x）：
  - L1: 1MB（代码中通常初始化 512KB）
  - L0A: 64KB, L0B: 64KB, L0C: 256KB
  - UB: 248KB（8 bank group × 2 bank × 16KB，注意 bank 冲突）
  - GM Workspace: 按需申请

硬件容量参考（A3/910B）：
  - L1: 512KB - 128B
  - L0A: 64KB, L0B: 64KB, L0C: 128KB
  - UB: 192KB（184KB Vec 可用）
  - GM Workspace: 按需申请

⚠️ FA Buffer 设计要点：
  - L1 预加载是 FA 性能的关键：Cube 在计算当前 tile 时，L1 预加载下一个 tile
  - UB 中 CrossCore 共享 buffer 需要严格的同步保护
  - Workspace 用于确定性计算时，需额外的 sync barrier
  - 新增特性复用已有 buffer 时，必须验证新数据量 ≤ buffer slot 容量
```

## 【F5】Online Softmax 精度链（必填，不可跳过）

```
问题：请填写 FA 精度链条，特别关注 Online Softmax 的精度处理。

  ┌─────────────────┬──────────┬──────────┬────────────┬─────────────────┐
  │ 计算步骤        │ 输入dtype│ 计算dtype│ 是否需Cast │ 精度说明        │
  ├─────────────────┼──────────┼──────────┼────────────┼─────────────────┤
  │ BMM1 (Q×K^T)    │ FP16/BF16│ FP32     │ Cube自升精 │ Cube 输出 FP32  │
  │ Scale (÷√d)     │ FP32     │ FP32     │ 否         │                 │
  │ Mask 应用       │ FP32     │ FP32     │ 否         │ -inf masking    │
  │ Softmax (exp/sum)│ FP32    │ FP32     │ 否         │ Online算法      │
  │ BMM2 (P×V)      │ FP16?    │ FP32     │ 需降Cast   │ P 需降到FP16    │
  │ Update (rescale) │ FP32    │ FP32     │ 否         │ 在线累积更新    │
  │ Output          │ FP32     │ FP16/BF16│ 需降Cast   │ 最终降精度      │
  └─────────────────┴──────────┴──────────┴────────────┴─────────────────┘

关键精度决策：
  1. BMM2 输入的 P 矩阵：Softmax 输出 FP32，送入 BMM2 前是否 Cast 到 FP16？
     （Cube 输入要求 FP16/BF16，但截断会损失精度）
  2. Online Softmax 的 m(max) 和 l(sum) 统计量：必须 FP32
  3. Update 的 rescale 因子 exp(m_old - m_new)：必须 FP32
  4. 最终输出的降精度时机和方式

精度验收标准：
  - FP16 输入：atol=1e-3, rtol=1e-3（对比标准 Attention）
  - BF16 输入：atol=2e-2, rtol=1e-2

⚠️ AscendC Tip：
  - ReduceMax / ReduceSum 的 mask 参数是实际元素个数，不是全 1
  - exp 计算可能产生 Inf（需先减 max 再 exp）
  - BF16→FP32 的 Cast 在 Cube 内自动完成，但 Vector 侧需手动 Cast
```

## 【F6】Mask 处理

```
问题：算子支持哪些 Mask 类型？每种 Mask 的处理方式是什么？

  ┌──────────────┬───────────────────┬──────────────────────────────┐
  │ Mask 类型    │ 数据来源          │ 应用方式                      │

## 【F7】确定性计算

```
问题：是否需要确定性计算保证？

关键场景：
  - 反向算子（FASG/SFAG 等）：梯度 dQ/dK/dV 的多核累加是否需要确定性？
  - 多核写同一输出地址：使用 AtomicAdd / ScatterAdd / Workspace 暂存后归约？
  - Online Softmax 的累加顺序：不同 tile 的处理顺序是否影响最终结果？

确定性设计选项：
  □ 不需要确定性（允许浮点累加顺序不固定）
  □ 需要确定性 — Workspace 方案（各核写独立区域，最后单核归约）
  □ 需要确定性 — 固定调度顺序（通过 sync barrier 强制顺序执行）
```

## 【F8】异常场景

```
问题：以下异常场景如何处理？

  - 空 Tensor（B=0 或 S=0）：PTA 层拦截 / 返回空 / kernel 内处理？
  - 超长序列（S > 某阈值，L1 无法一次放下一个 block）：动态分 block
  - head_dim 不对齐（D % 16 != 0）：pad 到对齐？在哪一层 pad？
  - 不支持的 dtype 组合：OpDef 约束 / PTA 层报错
  - NaN/Inf 输入：透传 / 截断 / 上报
  - Workspace 申请失败：回退策略？

A5 特殊场景：
  - Subnormal 数值：涉及 exp/log/sqrt/rsqrt 等运算时需配置计算模式
  - UB Bank 冲突：高并发 Load/Store 同一 bank group 时性能下降
```

## 【F9】同步正确性检查（新增，防死锁专项）

```
问题：请检查同步设计是否存在死锁风险，验证同步正确性。

⚠️ 关键要求：必须完成以下 5 类检查，输出同步正确性判定表。
   任何一项检查不通过，必须提供修复方案。

### 检查 1：SetFlag/WaitFlag 配对完整性（基础检查）

对每个同步事件，验证：
  (1) 每个 WaitFlag(event) 必须有唯一的 SetFlag(event) 与之配对
  (2) SetFlag 必须在 WaitFlag 之前执行（时间序）
  (3) 同一事件不能在同一代码路径上被重复 Set 或 Wait

检查方法：
  - 列出所有 SetFlag/WaitFlag 调用点
  - 构建配对矩阵，确保 1:1 映射

典型错误：
  ┌─────────────────────────────────────────────────────────────┐
  │ ❌ 错误：AIC Set(event0) → AIV Wait(event0) → AIV Set(event0) │
  │     问题：event0 被 AIC Set 后，AIV 又 Set，导致重复          │
  ├─────────────────────────────────────────────────────────────┤
  │ ❌ 错误：AIV Wait(event1)  // 但没有任何核 Set(event1)         │
  │     问题：永久等待，死锁                                      │
  └─────────────────────────────────────────────────────────────┘

### 检查 2：循环依赖检测（死锁核心检查）

验证 AIC↔AIV 之间是否存在依赖环：

典型 FA 流水依赖（无环，正确）：
  AIC(C1) ──SetFlag──→ AIV(V1) ──SetFlag──→ AIC(C2) ──SetFlag──→ AIV(V2)
       ↑___________________________________________________________|
                           (下一迭代形成环？需要检查)

死锁模式识别：
  ┌──────────────────────────────────────────────────────────────┐
  │ ❌ 死锁模式 1：交叉等待                                       │
  │   AIC: Set(e0) → Wait(e1)  // 等 AIV                          │
  │   AIV: Set(e1) → Wait(e0)  // 等 AIC                          │
  │   结果：双方互相等待，死锁                                     │
  ├──────────────────────────────────────────────────────────────┤
  │ ❌ 死锁模式 2：迭代间循环依赖（Ping-Pong）                    │
  │   偶迭代：AIC Set(e0_even) → AIV Wait(e0_even)                │
  │   奇迭代：AIV Set(e0_odd)  → AIC Wait(e0_odd)                 │
  │   问题：若偶/奇迭代事件 ID 规划错误，可能形成隐式环            │
  ├──────────────────────────────────────────────────────────────┤
  │ ❌ 死锁模式 3：多级流水反向依赖                               │
  │   C1→V1→C2→V2（正常）                                        │
  │   若 V2 需要通知 C1（如某种反馈机制），则形成环                │
  └──────────────────────────────────────────────────────────────┘

检查方法：
  1. 绘制依赖图：节点为流水阶段，边为 SetFlag→WaitFlag 方向
  2. 使用 DFS 检测环，若存在环则死锁
  3. 特别检查迭代间依赖（i 迭代的最后阶段与 i+1 迭代的最初阶段）

### 检查 3：CrossCore Buffer 访问序检查

FA 算子中 AIC 和 AIV 共享 UB Buffer（CrossCore），必须通过同步保护：

正确访问模式：
  ┌──────────────────────────────────────────────────────────────┐
  │ AIC 写入 CrossCore Buffer → AIC SetFlag → AIV WaitFlag        │
  │                                              ↓               │
  │ AIC SetFlag ← AIV 读取完成 ← AIV 读取 CrossCore Buffer        │
  └──────────────────────────────────────────────────────────────┘

检查清单：
  □ CrossCore Buffer 是否都有明确的"写完成→通知→读开始"序列
  □ 读后是否通知写方可以复用（避免覆盖正在读的数据）
  □ Ping-Pong Buffer 的同步是否正确（当前迭代读后，通知上迭代写）

典型错误：
  ┌──────────────────────────────────────────────────────────────┐
  │ ❌ 错误：AIC 写入 buffer → 立即开始下一轮写入（未等 AIV 读走） │
  │     结果：数据被覆盖，AIV 读到错误值                           │
  ├──────────────────────────────────────────────────────────────┤
  │ ❌ 错误：AIV Wait(e0) 后读取 buffer，但未通知 AIC 读完成       │
  │     结果：AIC 无法确认何时可以复用 buffer                      │
  └──────────────────────────────────────────────────────────────┘

### 检查 4：事件 ID 冲突与复用检查

事件 ID 规划表（必须输出）：
  | 事件 ID | 名称 | 发送方 | 接收方 | 使用范围 | 备注 |

检查项：
  (1) 事件 ID 唯一性：同一迭代内无重复
  (2) AIV1 偏移正确性：AIV1 事件 = AIV0 事件 + 16
  (3) Ping-Pong 隔离：偶/奇迭代事件 ID 不重叠
  (4) 事件数量限制：不超过硬件支持的最大值（如 32 个）

典型错误：
  ┌──────────────────────────────────────────────────────────────┐
  │ ❌ 错误：Ping-Pong 模式使用相同事件 ID                        │
  │   for (i=0; i<iter; i++) {                                    │
  │     if (i%2==0) { AIC Set(0); AIV Wait(0); }  // 偶迭代       │
  │     else        { AIC Set(0); AIV Wait(0); }  // 奇迭代       │
  │   }                                                           │
  │   问题：迭代 i 的 Set(0) 可能唤醒迭代 i+1 的 Wait(0)，导致     │
  │         i+1 在 i 完成前就开始，数据竞争                        │
  ├──────────────────────────────────────────────────────────────┤
  │ ❌ 错误：AIV1 事件 ID 未 +16                                  │
  │   AIV0: Wait(0), Wait(1)                                      │
  │   AIV1: Wait(0), Wait(1)  // 错误！应与 AIV0 区分              │
  │   正确：AIV1: Wait(16), Wait(17)                              │
  └──────────────────────────────────────────────────────────────┘

### 检查 5：异步事件丢失与超时防护

虽然 AscendC 同步原语是阻塞等待，但需考虑极端场景：

检查项：
  (1) 所有 WaitFlag 是否有对应的 SetFlag 保证点
  (2) 异常退出路径是否清理同步状态
  (3) 小张量保护（totalItems < usedCores）时，空闲核的同步行为

### 【必填】同步正确性判定表
